# Upgrading diracx in your cluster

!!! warning "Version compatibility"

    DiracX should be upgraded before upgrading legacy DIRAC installations.

Upgrades are managed via ``helm`` but can either be done manually, or in an automated way.

## Database setup

Replace `null` with `{}` for any built-in database you want to keep enabled in
an older values file, including files generated by `dirac internal legacy
generate-helm-values`. A `null` entry now removes the chart default from the
generated setup. Existing databases and stored connection secrets stay in place.

With bundled MySQL, the chart's SQL initialization job creates any missing
configured databases before upgrading the application. For external MySQL,
create the new databases and grant access before upgrading. See
[database management](../explanations/database-management.md) for connection
settings and defaults.

DiracX stores its transformation data in `DiracXTransformationDB`. Legacy
DIRAC stores its own transformation data in `TransformationDB`. The distinct
names let both databases coexist on the same MySQL server.

## Manual upgrade

First, update the ``values.yaml`` if you need to. Then simply run

``` bash
helm upgrade --timeout 3600s --wait --cleanup-on-fail <release-name> diracx -f my_values.yaml
```

## Automated update

Some tools can assist you managing clusters. There are two main tools: ``ArgoCD`` and ``Flux2``.

### ArgoCD

[ArgoCD](https://argo-cd.readthedocs.io/) is a very popular tool to manage clusters and automate releases. However, it does not play nicely with Helm charts using hooks for pre/post jobs, which ``diracx-charts`` does. Unfortunately, it means ``ArgoCD`` will not work for `diracx`.

### Flux

[Flux2](https://github.com/fluxcd/flux2) is an alternative which does not suffer from the hook flaws of ``ArgoCD``. However, in order to run, ``Flux2`` needs to have ``Operators`` available on the cluster, which some cluster do not allow (e.g. Openshift @ CERN).


### Gitlab automation

The steps involved into automating the release process using gitlab CI are easy, and are described in the [release how-to](make-a-release.md)
